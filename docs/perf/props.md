# Scene performance baseline

Generated by `npm run scene:profile`; the raw numbers are in `baseline.json`.

## How it was measured

- Commit `e22e153`, Chromium 149.0.7827.55, Node v24.19.0.
- Production build served by `astro preview`, page loaded with `?debug=perf`.
- Viewports: desktop 1440×900, mobile 390×844 with the CPU throttled 4× over CDP.
- Per section: the page scrolls from the top to the bottom of that section in 5 s while frames are recorded.
- **Draw calls / triangles**: `renderer.info` of each rendered frame (the shadow passes included), median over the section with the peak next to it; the loop skips frames once the picture is still, so only frames drawn during the scroll count.
- **Frame**: time between animation frames. On a real GPU the browser caps it at the display rate, so p50 sits at 16.7 ms; the tail (p95) is what shows jank.
- **Render**: time of `renderer.render` plus `gl.finish()`, i.e. CPU submission and GPU work together.
- **JS heap**: `Runtime.getHeapUsage` after a forced GC, at the end of the section.
- **gl-egl**: ANGLE (Intel, Mesa Intel(R) Iris(R) Xe Graphics (ADL GT2), OpenGL ES 3.2)
- **swiftshader**: ANGLE (Google, Vulkan 1.3.0 (SwiftShader Device (Subzero) (0x0000C0DE)), SwiftShader driver)

## Proposed budget

The starting targets hold as the **end goal** of phase C: ≤ 30 draw calls (shadow passes included), ≤ 50,000 triangles on desktop and ≤ 30,000 on mobile, frame p95 within one refresh on desktop (≤ 17 ms) and two on mobile with the CPU 4x slower (≤ 34 ms). Only the frame limits moved: the measure is quantized to the 16.7 ms refresh, so 16.8 is one refresh and not a miss.

**What the baseline says about getting there.** The desktop numbers are dominated by the shadows: three shadow-casting lights redraw all 63 casters every frame (188 draw calls and 75–99% of the desktop triangles, depending on the section) before the picture itself, which is 13–71 calls depending on the section. Mobile has no shadows and sits at 9–42 calls and under 17,000 triangles, so its triangle budget already holds; its calls and its frame time do not. The mobile frame p95 is 33–39 ms, and the Home section holds 34 ms with 9 calls while Work (20) and About (39) do not, so some of that cost is not the scene (the page scroll and the CSS3D layer share the throttled thread).

**Interim limits per ticket**, to be tightened as each one lands: T14 (merging) is expected to leave desktop under about 150 draw calls and 100,000 triangles and mobile under 30 calls; T15 (baked lights) removes the shadow passes of static geometry and should bring desktop under 60 calls and 50,000 triangles; reaching 30 calls on both needs the GLB meshes (keyboard, handles, books) merged as well, which no ticket of phase C plans yet. The door handles alone are 8,576 of the 31,982 triangles of the scene, four copies of a 2,144-triangle model.

SwiftShader numbers are a relative reference only (a frame there takes seconds); the budget is judged on the real GPU rows.
